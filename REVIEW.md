# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 36-37) | Grace period check compared integer minutes instead of seconds (`minutes > 10`). For `09:40:01` (601 seconds after a 09:30 shift start), `int(601 / 60) = 10`. The condition `10 > 10` evaluates to False, yielding 0 instead of 10. | Calling `compute_late_minutes` with punch-in `09:40:01` for shift `09:30` returned `0` instead of `10` as required by rule R2. | Changed grace evaluation to strictly compare elapsed seconds against 600s (`diff_seconds > 600`), then return `int(diff_seconds // 60)`. |
| 2 | `compute_late_minutes` (lines 34-36) | Replaced hour and minute directly on `punch_in` datetime without timezone conversion or handling overnight shifts. If `punch_in` is in UTC, replacing hour sets 09:30 UTC instead of 09:30 IST. | Passing a UTC datetime (e.g. `04:05:00Z` representing 09:35 IST) compared against 09:30 UTC, producing negative time deltas. | Converted `punch_in` to IST and constructed shift start datetime using the record's IST attendance date with `tzinfo=IST`. |
| 3 | `compute_work_hours` (lines 40-41) | Used standard Python `round()`, which uses banker's rounding (round-half-to-even) instead of round-half-up specified in rule R4. | Duration of 2.125 hours evaluated to `2.12` instead of `2.13` under half-up rounding. | Implemented `round_half_up` helper using `decimal.Decimal` with `ROUND_HALF_UP` quantizing to `0.01`. |
| 4 | `compute_overtime` (lines 44-47) | Returned overtime minutes for any positive value without enforcing the 30-minute minimum threshold (rule R3). | Punch-out at 18:35 for an 18:30 shift end returned `5` minutes overtime instead of `0`. | Only return overtime minutes if elapsed floor minutes >= 30, otherwise `0`. |
| 5 | `compute_overtime` (lines 44-46) | Did not handle overnight shifts (`shift_end <= shift_start`). Shift end on overnight shifts falls on the next calendar day (`date + 1 day`), but function assumed shift end was on `date_str`. | For overnight shift 22:00–06:00 on date 2026-07-06, punch-out at 2026-07-07 06:40 IST compared against 2026-07-06 06:00 IST, giving 1480 min overtime instead of 40 min. | If `shift_end <= shift_start`, advance the shift end calendar date by +1 day before computing time difference. |
| 6 | `GET /health` (lines 72-74) | Always returned `{"status": "ok"}` without pinging MongoDB. OpenAPI contract specifies 200 only if MongoDB answers a ping, else 503. | Stopping MongoDB still resulted in `GET /health` returning 200 OK. | Added `client.admin.command("ping")` within a try-except block, raising HTTP 503 on connection failure. |
| 7 | `POST /employees` (lines 79-85) | Relied on application check-then-insert (`find_one` then `insert_one`) without a database unique index, vulnerable to race conditions under concurrent requests. | Concurrent `POST /employees` with identical `emp_code` created duplicate documents in MongoDB. | Created unique index on `emp_code` at startup and caught `DuplicateKeyError` to return HTTP 409. |
| 8 | `POST /employees` (lines 53-61, 77-85) | Missing schema validations: `emp_code` regex (`^EMP\d{4,6}$`), name/department length limits, email regex, shift format regex, and missing check that `shift_start != shift_end`. | Sending `shift_start: "09:30"` and `shift_end: "09:30"` or invalid employee code returned 201 instead of 422. | Added strict Pydantic field validators matching OpenAPI schemas and validated `shift_start != shift_end`. |
| 9 | `POST /employees` (lines 81-85) | `created_at` returned as Python datetime/ISO string instead of integer epoch milliseconds (`EpochMillis`). | Client received ISO string instead of integer timestamp, violating OpenAPI `Employee` schema. | Converted `created_at` to epoch milliseconds integer using `dt_to_epoch_ms()` before serializing response. |
| 10 | `GET /employees` (line 93) | Off-by-one pagination error: `skip = page * page_size`. Since `page` starts at 1, `page=1` skipped the first 20 records. | Calling `GET /employees?page=1&page_size=20` returned records 21–40, omitting the first page entirely. | Fixed skip calculation to `skip = (page - 1) * page_size`. |
| 11 | `GET /employees` (line 94) | `total` counted the entire collection (`count_documents({})`) regardless of applied query filters. | Filtering by `department=Engineering` returned total count of all employees in database instead of filtered count. | Updated total count to `db.employees.count_documents(q)`. |
| 12 | `GET /employees` (line 95) | Missing sort clause. OpenAPI contract specifies results must be sorted by `emp_code` ascending. | Query returned records in arbitrary database natural order. | Added `.sort("emp_code", 1)` to cursor. |
| 13 | `POST /attendance/punch-in` (lines 100-101) | Did not handle unknown employee. If `emp_code` does not exist, `emp` is `None` and accessing `emp["shift_start"]` raised an unhandled `TypeError` (500). | Punching in with an unseeded/unknown employee code returned HTTP 500 instead of 404. | Added explicit check: `if not emp: raise HTTPException(404, "Employee not found")`. |
| 14 | `POST /attendance/punch-in` (lines 104-118) | Check-then-insert race condition. OpenAPI specifies: "Do not rely on check-then-insert. Concurrent punch-ins must yield exactly one 201 and the rest 409." | Simultaneous requests for the same employee and date both passed `find_one` and inserted duplicate logs. | Created compound unique index on `(emp_code, date)` and caught `DuplicateKeyError` to return HTTP 409. |
| 15 | `POST /attendance/punch-in` (lines 102-103) | Attendance date calculation ignored IST and overnight shifts (rule R1). A punch-in before shift end on an overnight shift belongs to the previous day's shift. | Punching in at 05:30 IST for overnight shift 22:00–06:00 was assigned today's date instead of yesterday's date. | Implemented `compute_record_date` checking if `shift_end <= shift_start` and IST time < `shift_end`. |
| 16 | `POST /attendance/punch-in` (line 102) | Did not truncate instants to whole seconds (rule R1). Milliseconds were preserved. | Millisecond values such as `.900` were saved and returned. | Truncated epoch milliseconds to whole seconds: `(ms // 1000) * 1000`. |
| 17 | `POST /attendance/punch-in` (lines 66, 100) | Allowed invalid status values. OpenAPI specifies only `PRESENT`, `WFH`, and `ON_DUTY` are accepted. | Sending `status: "ABSENT"` or `"LEAVE"` returned 201 instead of 422. | Enforced `Literal["PRESENT", "WFH", "ON_DUTY"]` in request schema. |
| 18 | `POST /attendance/punch-in` (lines 119-121) | Injected internal MongoDB ID `doc["id"] = str(res.inserted_id)`. Attendance records have no ID in the contract. | Response contained unwanted `"id"` key and raw datetime objects. | Removed `"id"`, popped `_id`, and serialized fields matching OpenAPI `AttendanceRecord`. |
| 19 | `GET /attendance` (lines 144-147) | Loaded all documents into Python memory (`list(db.attendance_logs.find(q))`) and sorted in Python. Exhausts memory and becomes unacceptably slow at 100k docs. | High latency and memory spikes on large collections. | Used MongoDB cursor `.sort([("date", -1), ("emp_code", 1)]).skip(skip).limit(page_size)` backed by compound index. |
| 20 | `GET /attendance` (line 145) | Sort order was only `date` descending, missing required secondary sort `emp_code` ascending. | Multiple records on the same date appeared in arbitrary order. | Applied compound sort `.sort([("date", -1), ("emp_code", 1)])`. |
| 21 | `GET /attendance` (lines 125-132) | Missing date range validation. OpenAPI specifies `date_from > date_to` must return 422. | Calling with `date_from=2026-07-10&date_to=2026-07-05` returned 200 with empty list instead of 422. | Added validation raising HTTP 422 when `date_from > date_to`. |
| 22 | `GET /attendance` (line 149) | Injected `"id"` attribute into returned records and returned unformatted datetime objects. | Response contained `"id"` field and unparsed ISO datetimes. | Removed `"id"` and formatted `punch_in`, `punch_out`, and `history` into epoch milliseconds integers. |
| 23 | Startup indexing (entire starter) | Starter created no database indexes at all, resulting in collection scans (`COLLSCAN`) and unenforced uniqueness. | Explain queries produced `COLLSCAN` and duplicate keys were permitted. | Created all unique and compound indexes inside FastAPI `lifespan` handler at application startup. |
| 24 | MongoClient configuration (line 22) | MongoClient initialized without `tz_aware=True`. Naive datetimes returned from PyMongo caused timezone bugs when calculating offsets. | Unaware datetimes raised errors or caused incorrect offset arithmetic when comparing with aware datetimes. | Configured `MongoClient(..., tz_aware=True)`. |

### Items examined and decided NOT to be defects
- **FastAPI error response format**: FastAPI's default error body `{"detail": ...}` for HTTP exceptions and `{"detail": [...]}` for validation errors matches OpenAPI specifications `Error` and `ValidationError`.
- **IST definition**: `timezone(timedelta(hours=5, minutes=30))` is standard and correct for India Standard Time (UTC+05:30).
- **Environment variables loading**: `load_dotenv()` followed by `os.getenv("MONGO_URI", ...)` ensures that injected OS environment variables take precedence over `.env` defaults, satisfying the environment contract.
